## 队友报告的实板性能

两张512×512演示图各预热1次、测5次，先取每图中位数再对两图平均：

| 方案 | 改动 | 耗时 |
| --- | --- | ---: |
| legacy48 | 每块打包，48×48输出核心，121次DMA往返 | 760.254 ms |
| fast48 | 整帧打包一次，仍为121块 | 659.752 ms |
| fast58 | 58×58输出核心，减少为81块 | 559.450 ms |
| compact58 | 返回有效核心，省去无用边界计算 | 523.226 ms |

报告的降时为31.18%，约1.453倍，都是**同一CNN在PL上的不同搬运/分块方案对比**，不能写成相对优化CPU的加速比。计时包含CPU打包、缓存同步、DMA、PL、轮询和拼图；不含读文件、参考计算与显示。也不能直接与我们256×256分割常驻网络的492.401 ms比较快慢。

bit SHA256：`d33786c2f16f8cf717ee4231a1d85ebb4d8c66ea95891df2c723730c137e0913`。此bit与我们的分割/基础处理bit不同，50 MHz设置也不同。

## 与现有项目的接法

1. 共享现有原始HU和空间信息，在网页增加独立的“LDCT增强”工作区；原HU→可选CNN/传统方法→增强HU→统一窗宽显示。不能把窗宽图、伪彩图或分割模型的0–1输入当作该模块HU输入。
2. 给统一板端服务增加独立LDCT硬件适配器，复用已审阅的分块函数和常驻缓冲区。它处理64×64内部块，不能当作当前固定512×512整帧基础算子直接发送。
3. 纳入现有单硬件所有者和健康/空闲切换逻辑；LDCT用50 MHz，分割用各自已验证的100 MHz，切换后分别读回校验。队友独立CLI直接加载Overlay、异常时复位DMA的流程不直接复制成网页请求处理器，需沿用我们故障保留硬件所有者的策略。
4. 可以选择将增强HU进一步用于分割和三维重建，保持尺寸、spacing、origin和direction；是否改善需独立专家标签确认。整卷处理时先批量增强、缓存HU，再一次切换到分割bit，避免每层反复加载bit。
5. 先接通工程与真实配对演示，再补充分辨率、整卷、异常情况和独立质量评价。若以后需要同一bit并行运行，再单独评估顶层集成、资源、时序和验证范围。

本次结论：该交接包可以作为LDCT模块集成的基础，下一步工作的重点是统一服务与HU数据流适配，以及补足完整效果评价；当前不需要重新从零开发CNN或重训后才能做初版展示。

给队友的具体时钟责任、Python签名、返回数据与故障状态约定见 [LDCT集成接口约定](ldct_integration_interface.md)。该文档是拟议接口，不表示当前部署包已经实现。
