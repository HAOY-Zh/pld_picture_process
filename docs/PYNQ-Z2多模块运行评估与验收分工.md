# PYNQ-Z2 多模块运行评估与验收分工

日期：2026-10-17。本文基于现有实现报告、冻结模型形状和服务代码作静态评估。本轮未连接或操作开发板，未构建所有模块合并的 bit，也未完成新增候选/配准的整机实测。

## 1. 能不能跑

**按“电脑持有整卷与三维、板端按切片/块计算、不同大模块分阶段加载 bit”的方式，现有证据支持继续集成；新增模块仍需资源、时序、内存和连续运行验收。**

不能从独立模块已经运行，推导出全部模块已经可以同 bit 并行、整卷实时完成，或整个新系统已经通过实板验收。

## 2. PL 资源核对

板卡为 XC7Z020 的 PYNQ-Z2，具有53,200 LUT、106,400 FF、140个36 Kb BRAM和220 DSP，配512 MB DDR3。来源：[板卡厂商规格](https://www.tul.com.tw/images/PYNQ-Z2_PA_v2_pp_20201209_STD.pdf)、[AMD器件数据手册](https://www.amd.com/content/dam/xilinx/support/documents/data_sheets/ds190-Zynq-7000-Overview.pdf)。DDR与片上BRAM是两类存储，不能混用容量。

| 已有设计 | LUT | FF | BRAM36 | DSP | 本次依据与状态 |
| --- | ---: | ---: | ---: | ---: | --- |
| 分割 exact-LUT | 17,268 | 18,455 | 31.5 | 80 | 实现及六组实板验收记录；网页尚未因此自动更换版本 |
| LDCT compact交接版 | 9,452 | 5,392 | 46.5 | 78 | 队友50MHz布局布线报告及测速记录；本机已审阅，尚未整机接入 |
| 基础六功能共享版 | 5,174 | 6,755 | 3 | 3 | 100MHz实现/仿真通过；新链路实板验收尚待回传 |
| 配准 | 待核实 | 待核实 | 待核实 | 待核实 | 不用软件原型估算代替综合/实现报告 |
| 新增候选初筛/ROI | 待实现 | 待实现 | 待实现 | 待实现 | 先固定最小算子和协议，再评价资源 |

前三项报告直接相加为31,894 LUT、30,602 FF、81 BRAM36、161 DSP，约占LUT60%、BRAM58%、DSP73%。这是**独立设计报告的粗略算术汇总**，不是合并结果。独立设计可能重复包含DMA/互连；共享资源、增加时钟/仲裁、布线和时序又会改变占用，因此既不能据此断言合并会失败，也不能承诺全部同bit一定能放下。

当前按不同bit运行时，只实例化当前阶段的硬件，资源不按所有已安装bit相加。阶段结束后确认真实空闲，再释放旧资源并切换；需要给活跃模块配置匹配的时钟。

同bit集成可作为后续优化：优先评价“基础处理＋轻量候选筛选”的共享通路；分割、LDCT与配准是否再合并，需完整顶层实现和验证，当前不作提交前承诺。

## 3. DDR 与 CMA 内存预算

目前代码将CT读取、原生尺寸恢复、三维清理、网格和MPR交给电脑：python/lung_live_web.py、python/lung_live_data.py、python/lung_volume_viewer.py。板端 pynq/ct_platform_service.py 管理当前网络/图像缓冲，健康空闲切换时先释放旧模式缓冲。

| 项目 | 静态规模 | 解释 |
| --- | ---: | --- |
| 512×512×300层 INT16 HU | 150 MiB | 单份整卷，不含元数据或副本 |
| 同尺寸 FLOAT32 HU | 300 MiB | 单份；原图与增强图各一份就达600 MiB |
| 原模型常驻特征CMA | 约7.47 MiB | 按22个输入/节点缓冲与保护区核算，非进程总内存 |
| 剪枝模型常驻特征CMA | 约7.16 MiB | 同上；按HWC8填充后的实际布局核算 |
| 当前基础处理发送＋接收CMA | 约2.00 MiB | 两个512×512 UINT32帧缓冲及保护余量 |
| LDCT两份64×64 UINT32块缓冲 | 32 KiB | 仅DMA块缓冲，另有整帧打包/输出等普通内存 |
| 基础链路最多8张INT16输入缓存 | 4 MiB原始数据 | 不含Python对象与压缩/返回过程中的临时副本 |

分割CMA依据 pynq/lung_fast.py 与原/剪枝 model.json，按每个形状的 H×W×ceil(C/8)×8 字节及16个UINT64保护字计算。其余权重准备、Python/NumPy、驱动、Linux与CMA管理仍占额外内存。512 MB物理DDR也不等于应用可分配内存或连续CMA可用量。

因此采用以下边界：

- 整卷HU、增强整卷、跨层连通域、候选列表和三维网格存于电脑；板端只接收当前切片/块，保留有上限的缓存。
- 不把完整三维CT和多个FLOAT32副本搬进板端Python，更不在ARM上重新跑完整病灶深度网络。
- 候选初筛由PL执行选定局部算子，三维连通域、形状排序和显示先放电脑，并在文档中写清执行位置。
- 未确认DMA空闲前不释放CMA。正常切换后的CMA复用/碎片化与故障保留导致的占用，需要实板监测，不能只看理论字节数。

## 4. 时延与调度

现有分割组合实测约492—553ms/256×256网络输入；LDCT交接报告约523ms/512×512切片，计时包含打包/DMA/PL/拼接。两者任务、输入和计时边界不同，不能直接据此比较算法效率。

作为排期与交互设计的粗预算，如果每层两个阶段各约0.5秒，那么100层连续执行两阶段就约100秒，再加传输、预后处理、切换等。这只是基于现有单切片结果的算术估计，不是新系统实测，更不能对外称为整卷实时。

推荐阶段调度：

1. 增强为可选阶段，先批量完成所需切片，增强结果回电脑缓存。
2. 一次切换到分割，连续计算所需层，肺掩膜回电脑。
3. 一次切换到候选/ROI通路，批量做初筛和计数；电脑做跨层合并与三维联动。
4. 配准由用户单独触发，处理指定图像对/ROI，不穿插进每层必经流程。

不能采用“第1层增强→分割→候选→第2层再重复三次加载”的调度。请求按硬件阶段串行执行，电脑显示与已算结果浏览可以继续响应；滑动MPR不应触发新的网络推理。

对整卷任务提供进度、已完成范围和层间取消；未计算层保持未知。分别记录bit切换、初始化、计算、网络往返和页面显示，保留单切片/局部与整卷两种交互方式。

## 5. 整机集成与验收统一由B（LDCT负责人）负责

根据用户最新指定，A负责肺结节候选算法与评价，B接手统一网页、服务、模块集成与整机验收，并收尾LDCT；C负责共用候选/ROI筛选与计数硬件。已有配准保留为可选拓展，不是主链路依赖。

B负责以下整机验收：

1. 汇总各模块实际实现资源、目标/读回时钟、bit/HWH与驱动版本；缺失项明确列出，不替模块负责人猜测。
2. 在统一服务入口下，执行基础→LDCT→分割→候选→配准的可用阶段切换用例。未完成阶段标为待测，不另开服务抢占硬件。
3. 记录切换前后DMA状态、PL/ARM时钟、CMA可用量、进程内存和输出正确性；重复切换/连续帧后检查内存持续增长、旧结果误用、超时与错频。
4. 对相同输入区分冷启动/热运行、同bit换参数/跨bit切换、PL计算/往返/网页端到端，保留逐次原始记录。
5. 交付一份整机验收矩阵、原始回执和资源/时延图表，用于报告和现场排练。

B负责统一验收、定位跨模块问题及修复服务/页面/LDCT；A修复候选算法，C修复共用筛选/计数的硬件与驱动。模块负责人各自提供资源、时序、版本、自检输出和计时，B汇总而不替所有人重做模块验证。

为平衡工作量，共用候选/ROI硬件从B移交C，使B集中增强收尾与整机；A先交最小候选软件闭环和参考向量，C据此做硬件。配准按已有成果保留，不同时增加完整病灶网络、多模态配准或大规模算法搜索。详细交付见 [三人分工与提交前推进计划](三人分工与提交前推进计划.md)。

## 6. 当前结论的证据边界

已有分割和LDCT独立运行证据、基础共享bit实现证据，以及当前主机/板端架构，支持采用切片/分块与分阶段复用的集成方案。**新增候选和配准资源未知，完整新链路尚未验收。**

当前主要风险是整卷耗时、CMA/普通内存峰值、频繁切bit、候选误报，以及新模块时序和协议；不能仅以LUT/DSP仍有余量判定全部功能已经“跑得动”。最终以匹配版本的实板输出、资源、时钟、内存与端到端记录作结论。
