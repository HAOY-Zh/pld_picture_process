# 从零部署与团队协作

本文件对应 GitHub `main` 的原集成架构：电脑负责网页、采样、量化及原有预后处理；板端提供现有 FPGA 核心计算。没有采用 PS 网页迁移、EDCNN 或未验收的新硬件。使用仓库已有 bit/HWH 和冻结权重，不需要重新训练，也不需要安装 Vivado 来运行。

以下步骤适用于**两端都没有本项目文件**的首次部署，不需要维护者私有软件包或原令牌。电脑必须已有 Windows 10/11 x64；PYNQ-Z2 必须先能启动 PYNQ 系统。裸 SD 卡不能只复制本仓库就开机。

## 1. 先准备系统和网络

**板子**：从 [PYNQ 官方下载页](https://www.pynq.io/) 的 Previous downloads → PYNQ-Z2 下载 **v3.1.1** 镜像，按 [官方 PYNQ-Z2 指南](https://pynq.readthedocs.io/en/v3.1/getting_started/pynq_z2_setup.html) 写入新的/确认可清空的 microSD 卡，启动跳线置 SD，并接好电源和网线。写镜像会覆盖所选 SD 卡；这不是给已有运行板子升级的步骤，不要对正在使用的 SD 卡直接操作。

电脑与板子需要网络互通。官方直连默认板子地址是 `192.168.2.99`，电脑有线网卡可设为 `192.168.2.10`、掩码 `255.255.255.0`，该有线网卡不用填网关/DNS；电脑可继续通过 Wi-Fi 上网。改网卡前记下原设置。接路由器时使用板子实际分配的 IP，下面安装命令里的地址也要一致替换。

先在浏览器打开 `http://192.168.2.99/` 的 PYNQ/Jupyter 页面并登录；官方镜像默认账户见上述官方指南。使用镜像实际提供的 Jupyter 地址；本项目的 **8766** 是后续 FPGA 服务端口，不是 Jupyter 入口。

**电脑**：安装 [官方 Python 3.11.9 Windows x64](https://www.python.org/downloads/release/python-3119/)（保留 Python Launcher 和 pip）。如电脑没有 Microsoft C++ 运行库，安装 [微软官方 x64 Visual C++ Redistributable](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist)。不需要 CUDA、Anaconda、PYNQ 或 Vivado。

电脑首次安装必须能访问 PyPI 和 `download.pytorch.org`。板端 PYNQ 镜像应有 NumPy、PYNQ 和 `g++`；后面会先检查。若缺少 `g++`，需要让板子临时联网安装它，再继续，不能跳过。

## 2. 下载 main 并安装电脑依赖

从 [GitHub main](https://github.com/HAOY-Zh/pld_picture_process/tree/main) 下载完整 ZIP 并解压到短、可写的目录，例如 `C:\CTStudio`。后续在源码根目录打开 PowerShell。不要在 ZIP 预览里运行，不要只下载几个 Python 文件。

```powershell
py -3.11 --version
py -3.11 -m venv .venv-web
.\.venv-web\Scripts\python.exe -m pip install -r deployment/requirements-windows-cpu.txt
.\.venv-web\Scripts\python.exe -m pip install torch==2.8.0 --index-url https://download.pytorch.org/whl/cpu
.\.venv-web\Scripts\python.exe -m pip check
```

依赖清单固定为原已使用的版本；Torch 使用官方 CPU 构建，保留原量化和预后处理，核心推理仍走 FPGA。这些安装命令只用于首次准备环境，不是日常启动步骤。每条命令成功后再执行下一条；下载失败时先修复网络，不要更换未知来源的模型或依赖。

## 3. 一次生成电脑和板端共用的新配对

确认板子 IP 后执行（示例使用官方默认 IP）：

```powershell
.\.venv-web\Scripts\python.exe -B -X utf8 python/ct_studio_integration_release.py install --board-url http://192.168.2.99:8766
.\.venv-web\Scripts\python.exe -B -X utf8 deployment/verify_installation.py
```

必须看到 `PASS_LOCAL_DEPENDENCIES_AND_ASSETS`。它会核对八项电脑依赖、全部资产/嵌套清单、LDCT 和结节模型契约；不连接板子，也不提交计算。

这一步使用仓库自带的 `runtime/ct_studio_integration_20261025/ct_studio_integration_runtime.zip`，在本地生成：

```text
data/ct_studio_integration_20261025/
  host_config.json
  host_platform.json
  shared_host_platform.json
  model.json
  installation.json
  platform_token.txt
  ct_studio/              # 完整板端资产、驱动、冻结模型和合成自检
```

其中 `ct_studio/` 必须原样送到板子。**只能生成一次，再将这一份复制给板端；不要在电脑和板端各安装一次。** 两次安装会产生不同令牌/清单。重新执行安装命令遇到“目录已存在”是保护机制：此时继续验证现有配对，不要删除后重新生成令牌。

导出板端传输 ZIP，并显示配对身份（身份哈希不是令牌）：

```powershell
.\.venv-web\Scripts\python.exe -m zipfile -c data/ct_studio_board.zip data/ct_studio_integration_20261025/ct_studio
(Get-Content data/ct_studio_integration_20261025/installation.json -Raw | ConvertFrom-Json).service_bundle_sha256
```

记下输出的 64 位哈希。该 ZIP 含刚生成的私有令牌，只在本机与目标板子之间传输，**不要上传 GitHub**。仓库公开 ZIP 不含维护者原令牌；新配对不会自动连接现有旧配对服务。

## 4. 把完整板端包送到全新板子并核对

在 Jupyter 文件页的根目录上传 `data/ct_studio_board.zip`，再打开 New → Terminal。以下以它位于 `/home/xilinx/jupyter_notebooks/ct_studio_board.zip` 为例；先用 `ls` 核对真实上传位置。

```bash
/usr/local/share/pynq-venv/bin/python3 -c "import numpy,pynq; print(pynq.__version__)"
command -v g++
```

要求 PYNQ 为 3.1.1，并且能找到 `g++`。若没有编译器，先让板子联网，再运行 `sudo apt-get update` 和 `sudo apt-get install -y g++`。电脑环境不要复制到板子；板端不安装 Torch。

使用一个不存在的新目录解压（`mkdir` 报目录已存在就先检查，不能继续覆盖）：

```bash
ls /home/xilinx/jupyter_notebooks/ct_studio_board.zip
mkdir /home/xilinx/ct_studio_fresh
/usr/local/share/pynq-venv/bin/python3 -m zipfile -e /home/xilinx/jupyter_notebooks/ct_studio_board.zip /home/xilinx/ct_studio_fresh
cd /home/xilinx/ct_studio_fresh/ct_studio
```

把下方占位文本替换成第 3 步电脑输出的 64 位身份哈希，然后完整执行：

```bash
export EXPECTED_MANIFEST='替换成电脑输出的64位哈希'
/usr/local/share/pynq-venv/bin/python3 - <<'PY'
import hashlib, os, re
from pathlib import Path
expected = os.environ['EXPECTED_MANIFEST']
assert re.fullmatch('[0-9a-f]{64}', expected), '先填写电脑端输出的身份哈希'
assert hashlib.sha256(Path('platform_manifest.json').read_bytes()).hexdigest() == expected, '电脑与板端不是同一份安装包'
from ct_studio_shared_service import validate_package
validate_package(Path.cwd())
print('BOARD FILES AND PAIRING PASS')
PY
```

没有看到 `BOARD FILES AND PAIRING PASS` 就停止，不要启动硬件服务。

## 5. 首次启动和设置开机服务

此步**只用于没有其他 FPGA 所有者的全新板子**。已有程序运行的板子，必须先由维护者确认它空闲并正常退出，不能强杀、不能同时运行两个所有者。本交接不要求更改你当前正在使用的板子。

先检查当前没有进程持有项目硬件锁、没有监听 8766。以下只读检查不会重载硬件：

```bash
/usr/local/share/pynq-venv/bin/python3 - <<'PY'
import fcntl, socket
with open('/tmp/lung_live_z2.lock', 'a') as lock:
    fcntl.flock(lock, fcntl.LOCK_EX | fcntl.LOCK_NB)
    with socket.socket() as port:
        port.bind(('0.0.0.0', 8766))
print('OWNER AND PORT IDLE')
PY
```

仅在前述检查通过且 `EXPECTED_MANIFEST` 仍在同一个终端中时，创建独立开机单元：

```bash
if [ -e /etc/systemd/system/ct-studio-fresh.service ]; then
    echo '服务文件已存在，保留它并停止本次安装；不要覆盖或重复启动。'
else
    sudo tee /etc/systemd/system/ct-studio-fresh.service >/dev/null <<EOF
[Unit]
Description=CT Studio shared FPGA platform
After=network.target bootpy.service
RequiresMountsFor=/home/xilinx/ct_studio_fresh/ct_studio

[Service]
Type=simple
User=root
WorkingDirectory=/home/xilinx/ct_studio_fresh/ct_studio
Environment=PYTHONUNBUFFERED=1
Environment=PYTHONDONTWRITEBYTECODE=1
Environment=XILINX_XRT=/usr
Environment=VIRTUAL_ENV=/usr/local/share/pynq-venv
Environment=PATH=/usr/local/share/pynq-venv/bin:/opt/microblazeel-xilinx-elf/bin:/opt/python3.10/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
ExecStart=/usr/local/share/pynq-venv/bin/python3 -B -u /home/xilinx/ct_studio_fresh/ct_studio/ct_studio_shared_owner.py --folder /home/xilinx/ct_studio_fresh/ct_studio --expected-manifest ${EXPECTED_MANIFEST} --port 8766
Restart=no
TimeoutStartSec=infinity
TimeoutStopSec=infinity
SendSIGKILL=no
UMask=0077

[Install]
WantedBy=multi-user.target
EOF
    sudo systemd-analyze verify /etc/systemd/system/ct-studio-fresh.service &&
    sudo systemctl daemon-reload &&
    sudo systemctl enable --now ct-studio-fresh.service
fi
```

这里直接使用公开包内已配套的 **`ct_studio_shared_owner.py`**，包含共享结节核；不要换成历史基础服务或 `ct_studio_boot.py` 的旧入口。

首次启动会编译本地 MMIO 加载器并执行实际 FPGA 自检，需要等待。`systemctl` 显示 active 只代表进程存在，**不代表硬件自检通过**：

```bash
sudo journalctl -u ct-studio-fresh.service -n 60 --no-pager
cat /home/xilinx/ct_studio_fresh/ct_studio/owner_state.json
```

应看到 `CT STUDIO SHARED READY`，`owner_state.json` 为当前启动的 `phase: ready`。若是 `failed_owner_retained`，保留日志并联系维护者；不要重复提交推理、自动重载或强杀后再试。运行中正常停止使用 `sudo systemctl stop ct-studio-fresh.service`，它会等当前任务和 DMA 确认空闲后退出。

## 6. 电脑验收，然后日常双击启动

回到电脑的源码根目录：

```powershell
.\.venv-web\Scripts\python.exe -B -X utf8 deployment/verify_installation.py --board
```

必须看到 `PASS_PAIRED_BOARD_READINESS`。这会同时核对原接口和共享结节服务的实际身份、启动验收及空闲状态；它只读状态，不提交推理、不停止服务。403 表示配对不一致，身份不一致表示连接的服务版本不配套，都应先检查第 3–5 步，不要重装电脑来更换令牌。

验收通过后，日常只需：板子上电并等就绪 → 双击源码根目录 **`start_ct_studio_integrated.cmd`**。网页默认 `http://127.0.0.1:8099/`。系统重启后板端由开机服务启动；电脑仍需双击入口。首次验证可用 `python/create_demo_ct.py` 生成合成 CT 检查导入；实际效果与整例检测需用自己合法取得的 CT 验收，患者数据不在 GitHub。

交付完成条件：本地检查通过、板端文件检查通过、实际共享服务自检通过、电脑配对检查通过、网页启动且实际处理任务完成。这些条件逐项记录；离线通过不能写成“已重新刷卡实测全部通过”。

## 7. 队友如何修改和合入

仅使用现成程序可以 Download ZIP；要提交代码，安装 [Git for Windows](https://git-scm.com/download/win) 并通过自己的 GitHub 账户使用 Git。不要在压缩包副本里长期修改后直接覆盖 main。

有仓库写权限时，先从最新 main 开自己的分支，例如：

```powershell
git clone https://github.com/HAOY-Zh/pld_picture_process.git
cd pld_picture_process
git switch main
git pull --ff-only origin main
git switch -c teammate/nodule-improvement
```

在这个工作目录完成第 2–6 步；保存好同一份本地配对，更新源码时不要重新安装产生新令牌。检测入口见 [检测文件映射](同学交接说明_20261026.md#肺结节检测从哪里修改)。优先改 `python/nodule_detector.py`、`python/nodule_vendor/lung_nodule_cnn.py` 的候选处理和 `python/lungseg/workspace/nodule*.js` 的界面；改模型/量化/协议时必须重新配套并上板验收。

修改源码后，先等旧网页任务结束，再在启动日志 `data/ct_studio_demo_launcher/<实例>/web.pid` 中确认自己的后台 PID，通过任务管理器结束该本机后台，再双击入口。仅关浏览器不会卸载旧 Python 模块；使用已经配对的私有软件包开发时，也可沿用 `start_ct_studio_dev.cmd` 的源码变化检测入口。

需要运行的核心回归：

```powershell
$env:PYTHONPATH='python;python/tests;pynq;pynq/roi_vendor'
.\.venv-web\Scripts\python.exe -B -X utf8 -m unittest test_basic_single_path test_ct_platform test_ct_platform_fast test_ct_workspace test_ct_studio_boot test_integration_release test_nodule_speed test_nodule_online test_ct_nodule_workspace test_ct_roi_workspace test_ct_studio_shared
.\.venv-web\Scripts\python.exe -B -X utf8 -m unittest test_ct_workspace_desktop
.\.venv-web\Scripts\python.exe -B -X utf8 -m unittest discover -s desktop -p "test_*.py"
```

测试之外，还要记录实际板端运行结果，特别是坐标/来源绑定、候选顺序、尾批、取消、错误不回退和整体耗时。结节原始分数不是恶性概率；改变检测效果要有独立评价，不能只凭程序跑通。

确认修改范围后，**明确列文件提交**，下面的路径只是肺结节修改示例，按实际改动调整：

```powershell
git status --short
git diff --check
git diff -- python/nodule_detector.py python/nodule_vendor/lung_nodule_cnn.py python/lungseg/workspace/nodule.js
git add -- python/nodule_detector.py python/nodule_vendor/lung_nodule_cnn.py python/lungseg/workspace/nodule.js
git diff --cached --stat
git commit -m "Improve nodule candidate handling"
git push -u origin teammate/nodule-improvement
```

到 GitHub 从自己的分支向 `main` 发 Pull Request，说明改动、测试和实板结果，由维护者审查合并。没有写权限时先 Fork，克隆自己的 Fork 并以本仓库 main 为基础开分支，然后发跨仓库 PR。合入前 main 若更新，先把最新 main 合并到自己的分支、处理冲突并重新测试，不要强推 main。维护者合并后，其他成员再 `git pull --ff-only origin main` 更新。

`data/`、`.venv-web/`、令牌、板端传输 ZIP、真实 CT/结果、训练数据及临时工程都不提交；新增第三方依赖写入相应依赖清单，新增源码文件要明确加入 Git。不要使用 `git add .` 把运行目录一起提交。涉及冻结硬件/模型资产时，先更新来源、契约、清单和验收记录，不能直接覆盖原 ZIP 还沿用旧结论。
