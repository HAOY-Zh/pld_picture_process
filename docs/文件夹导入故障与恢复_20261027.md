# 文件夹导入故障与恢复（2026-10-27）

实际故障：8099 仍可返回 HTTP 200，但浏览器选择文件夹时显示 `Failed to fetch`，本机只收到 251 个文件。路径读取正常。路径入口由电脑直接读取源文件；文件夹选择入口需经浏览器逐个上传，因此有额外的文件读取与 HTTP 传输环节。本次没有取得浏览器底层网络错误码，不能断言中断一定由单一原因造成。

已在当前 `data/CT_Studio_ExactSpeed_20261027_04` 应用补强：

- 每次先读取一个文件的字节，再发送，避免直接以磁盘 File 对象作为上传请求体；仍保留单文件 64 MiB 和整组 2 GiB 限制。
- 上传专用服务器等待时间由 10 秒调整为 120 秒；不改变 FPGA 命令超时。
- 网络中断最多重试两次，重复请求必须编号、原文件名、大小和 SHA256 完全相同，才算同一次接收；不同内容不能覆盖原文件。
- 非法 DICOM 等明确校验错误不重试；错误显示文件编号和名称。本机文件读取失败、服务连接失败和上传超时提供可读说明。
- 文件数量和总字节没有完整接收时，不能将残缺序列标记为导入完成。

验证：5 项后端重试语义测试、浏览器上传辅助函数的连接中断/本机读取失败/有限重试测试通过。独立实际 HTTP 服务完整接收 300 个匿名合成 DICOM，逐文件 SHA 一致、几何检查通过；随后在用户当前内置浏览器的实际 8099 页面，通过“选择 CT 文件夹”完整导入同一组 300 个文件，界面显示 1 组 300 层序列且检查通过，全部上传文件再次与源文件核对一致。合成文件是小尺寸测试，不等于所有大文件与浏览器异常都已覆盖。
