# LDCT 模块接入与 100 MHz 优化交接要求

日期：2026-10-17  
适用项目：低剂量 CT 增强与智能分析辅助系统  
交接目标：让现有 LDCT 硬件模块能够接入统一网页与板端服务，并验证提高到 100 MHz 后的实际收益。

**负责人更新：LDCT负责人同时接手整机集成与验收；原平台负责人转做肺结节候选；第三人负责共用候选/ROI筛选及计数硬件。** 本文的“处理类”和“统一服务”仍是两个职责层，即使由同一人维护，也由服务统一管理bit、时钟和资源。完整安排见 [三人分工](三人分工与提交前推进计划.md)。

## 一、这次希望完成什么

当前交接包已经具备 CNN 去噪、传统滤波、bit/HWH 和板端运行脚本，可以在此基础上封装，无需重写算法或网页。

希望按下面的顺序推进：

1. **先提供可重复调用的板端 Python 接口**，支持当前已经验证的 50 MHz 版本。
2. **尝试提供通过时序和实板验证的 100 MHz 版本**，接口保持一致，保留 50 MHz 版本作对照。
3. 补齐实际 FPGA 输出数组、逐次测速和版本信息，便于我们接入、复核和撰写比赛文档。

LDCT负责人负责模块驱动封装、硬件版本、整数参考和模块验证，并接手现有网页、HTTP服务、CT公共输入、MPR/三维联动及统一硬件管理。原平台负责人交接已有代码/启动步骤/验证记录，并负责肺结节候选算法与数据适配；第三人交共用筛选/计数硬件。100 MHz优化与初版接入可以并行推进。

## 二、50 MHz 与 100 MHz 的要求

### 为什么值得尝试 100 MHz

在每张图所需计算周期不变且硬件时序正确的前提下，50 MHz 提升到 100 MHz，PL 计算部分的时间理论上可以减半。但整帧还包括 PS 打包、缓存同步、DMA、轮询和拼接，因此**不能把目前约 523 ms/张直接除以 2，当作最终性能**。

现有 523.226 ms 是交接报告中两张 512×512 样例的 compact58 方案汇总值，包含上述整帧处理过程。此前 760.254→523.226 ms 是同一 CNN 的 PL 分块/搬运优化对比，不是 CPU 与 FPGA 的加速比。

### 100 MHz 版本需要交付什么

- 在 **100 MHz 目标约束下重新完成综合、布局布线**，提供匹配的 bit、HWH，以及相关源码/构建脚本。
- 提供布局布线后的 setup、hold、DRC 和资源报告，确认相关路径已正确约束并通过时序检查。
- 在板端读回实际 PL 频率；使用相同权重、相同输入、相同分块方案和计时范围，与 50 MHz 版本比较。
- 核验 100 MHz 的实际输出与相同整数参考逐像素一致，并回传输出 NPY 和原始耗时记录。
- 使用独立版本号和 SHA256，保留原来可工作的 50 MHz 包。

**不能只在 Python 中把现有 50 MHz bit 的时钟改为 100 MHz，就认定升级成功。** 若 100 MHz 暂时不能通过时序或实板验证，请记录问题，继续交付稳定的 50 MHz 接口，不阻塞平台接入。

### 谁设置时钟

| 事项 | 责任方 |
| --- | --- |
| 在清单中声明本版本所需频率和容差 | LDCT 模块负责人 |
| 获取硬件锁、加载 bit、设置 FCLK0 | 统一服务，由LDCT/整机负责人维护 |
| 每帧开始和结束读取频率并校验 | LDCT 处理接口 |
| 保持 ARM 频率不变并记录实际值 | 统一服务及对照测试脚本 |

LDCT 类只读取、检查时钟，不自行修改 FCLK、PLL 或 CPU 设置。当前可以沿用 0.5 MHz 的检查容差，实际读回值必须记录。

当前分割使用已验证的 100 MHz，LDCT 交接版使用 50 MHz。整机负责人需在统一服务中增加按模块版本切换时钟的逻辑：确认旧任务空闲后释放资源，核验并加载新 bit，在引擎未启动时设置频率，读回校验后再接收任务。**现有平台尚未完成 LDCT 的这部分适配。**

## 三、希望提供的 Python 接口

建议新增 `ldct_processor.py`，基于已有 `run_frame_fast` 封装。下面是拟议接口，名称可以协商，资源所有权和数据语义请保持一致。

```python
processor = LDCTProcessor(
    dma=overlay.axi_dma_0,
    gpio=overlay.axi_gpio_0,
    tx_buffer=tx_buffer,
    rx_buffer=rx_buffer,
    model_dir=model_dir,
    read_clock_mhz=lambda: float(Clocks.fclk0_mhz),
    expected_clock_mhz=50.0,  # 从本版本清单读取；100 MHz 版填其声明值
    timeout_s=10.0,
)

result = processor.process_slice(hu, method="cnn")
enhanced_hu = result["hu"]
processor.assert_idle()
state = processor.get_state()
```

要求一次初始化后能连续处理多张切片。构造函数和导入模块时不启动 DMA，也不运行完整 CPU CNN 参考。

统一服务传入已经加载的 DMA/GPIO 和两份常驻、物理连续的 `uint32` CMA 缓冲区；当前每份 4096 个元素即可覆盖 64×64 内部块。处理类借用这些对象，不自行创建 Overlay、不释放外部缓冲、不重烧 bit、不退出进程。并发请求由统一服务串行调度，不要求模块内部同时处理多个请求。

### 输入约定

- 输入是非空二维 NumPy **原始 HU 数组**，支持 `int16` 和 `float32`，不是窗宽图、伪彩图或 0～1 归一化图。
- 浮点沿用现有 `np.rint` 舍入语义，检查有限值和 INT16 范围后转换；越界拒绝，不静默裁剪。
- 至少支持 512×512；其他支持尺寸及边缘块规则写入清单。64×64 内部块、CNN halo=3、58×58 有效核心及 compact 协议由模块内部处理。
- 未知方法、非法形状和非法数值应在 DMA 启动前拒绝。清单列明方法名称与硬件 mode 的对应关系。

### 输出约定

```python
{
    "hu": enhanced_hu,  # 独立的 int16 数组，与输入 H×W 和像素位置一致
    "total_ms": 523.2,  # 仅为字段示例，必须返回此次实际测量值
    "timing_scope": "pack+cache+DMA+PL+poll+stitch",
    "actual_pl_mhz_before": 50.0,
    "actual_pl_mhz_after": 50.0,
    "tiles": 81,       # 此次实际块数
    "method": "cnn",
    "model_id": "实际模型版本或检查点SHA256"
}
```

输出不加显示窗、不缩放、不改变像素坐标，不能返回下次 DMA 会覆盖的缓冲视图。CT 的 spacing、origin、direction 由统一平台保留，使增强结果可以继续用于显示、分割和三维重建。

`total_ms` 从本帧打包前计时，到完成拼接并得到独立结果数组时结束，包含必要的缓存同步、DMA、PL 和轮询。不计读文件、bit 下载、初始化、绘图或完整 CPU 参考。如果没有硬件计数器，不必提供“纯 PL 时间”；可选分项计时应说明边界。

## 四、空闲和故障接口

希望 `get_state()` 至少返回：

```python
{
    "busy": False,
    "faulted": False,
    "dma_may_access": False,
    "error": None
}
```

- 在可能启动任一 DMA 传输前，先置 `dma_may_access=True`；部分启动后异常也必须保留该状态。
- 只有确认发送和接收均已完成、不再访问内存且无硬件错误，才能清除该标志。
- `assert_idle()` 应检查真实状态，不确定就报错，不能通过复位来假装空闲。
- 超时、DMA 错误和 PL 协议错误要向上抛出并保留故障状态，不自动重试、不自动复位、不释放缓冲、不偷偷返回 CPU 结果。
- 统一服务负责后续恢复和资源释放。已有独立 CLI 中的自动复位/释放流程，不直接搬进借用外部资源的处理类。

这些约定用于保证后续切换基础处理、LDCT 和分割 bit 时，旧硬件不会继续访问已经释放的内存。接口故障状态可用模拟对象验证，不要求故意在板上制造总线挂死。

## 五、交付文件和版本信息

可以沿用现有部署包布局，请补齐以下内容：

| 内容 | 要求 |
| --- | --- |
| 调用接口 | `ldct_processor.py`、最小调用示例及所需依赖版本 |
| 硬件 | 每个频率版本匹配的 bit/HWH、RTL/ROM、构建脚本与时序/资源报告 |
| 模型 | 匹配的整数权重、量化配置、整数参考、模型版本及 SHA256 |
| 清单 | 板卡、时钟域/频率/容差、IP 名称、GPIO 配置布局、流打包与返回协议、输入输出类型、支持尺寸/方法、文件 SHA256 |
| 验证 | 输入与正常剂量参考、实际 FPGA 输出 NPY、逐像素核验记录、逐次计时 CSV/JSON、运行环境与读回频率 |

清单建议新增 `interface_version="ldct_slice_v1"`；明确 HU→HU、输出 `int16`、内部块上限、halo、有效核心和 compact 支持。已有配置可以复用，不需要重复维护两套。

当前已交接模型是三层残差 CNN（1→8→8→1），权重写入 RTL ROM。若更换后续新训练权重，必须同步更新 ROM、重建 bit，并保证整数参考、权重文件、bit 和输出记录属于同一版本，不能只替换 NPZ。

## 六、验证与性能对照怎么做

### 初版接入验收

1. 同一初始化对象连续处理现有两张 512×512 样例，每张输出与对应整数参考逐像素一致。
2. 覆盖边缘块、非整除核心尺寸以及清单声称支持的方法；非法输入在 DMA 前拒绝。
3. 错误频率在 DMA 前拒绝；正常帧处理前后频率符合清单。
4. 回传实际 FPGA 输出数组，不能只给输出哈希，也不能用电脑参考数组代替 FPGA 输出。

### 50/100 MHz 速度对照

- 固定权重、输入、ARM 频率、分块方案、驱动优化和计时边界，只改变经过验证的硬件频率版本；若其他因素也改变，单独说明。
- 建议各预热 3 次、正式测量 20 次，交错测试或重复测试阶段，保留所有逐次记录。
- 报告平均值、中位数和 P95，以及实际频率、输出一致性和资源/时序情况。
- 同时保留 `legacy48 / fast48 / fast58 / compact58` 的现有结果，以区分搬运/分块优化与提频收益，不要求每次网页请求都跑这些对照。

后续若增加 CPU/FPGA 加速比，请使用同一输入、同一模型和明确的精度/计时范围。CPU FP32、CPU 整数参考和 PL 整数执行要分别标注，不能把低效参考脚本的耗时直接当成优化 CPU 基线。

## 七、效果评价需要补充什么

初版可以先用已有配对 LDCT/正常剂量样例演示，但两张切片只能作为演示，不能代表完整测试集效果。后续请补充：

- 数据来源、患者级训练/验证/测试划分，以及模型是否用过演示病例。
- 在固定测试集上对原始 LDCT、增强结果和正常剂量参考计算质量指标；HU 域 RMSE 可直接报告，PSNR/SSIM 应声明数据范围和处理规则。
- 如需展示量化损失，提供与当前整数模型对应的 FP32 检查点、推理说明和对照结果。

本轮不要求另外制作肺部专家标签。没有对应标签和独立实验时，只表述“增强结果可接入后续分割/三维流程”，不宣称已经提高分割 Dice 或三维精度。

## 八、本轮完成标准

**优先完成：稳定可调用接口 + 匹配的 50 MHz 包 + 实际输出及测速记录。**

**性能目标：尝试 100 MHz，只有通过时序、输出一致性和实板测速后才作为可用升级版。**

新模型训练、更大规模质量评价、同一 bit 多 IP 并行可作为后续工作，不阻塞本轮接入。当前多个模块仍按任务切换 bit；若将来同 bit 并行，需要另行处理顶层资源、时钟域与跨域通信。
